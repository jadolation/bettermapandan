## Project Overview

Better Mapandan is an independent transparency portal for the Municipality of Mapandan, Pangasinan, built under the [BetterGov.ph](https://bettergov.ph/) BetterLGU initiative. It is a **static, client-rendered site** generated by a Python build pipeline.

**What it covers:**

- 1,000+ services across 13 categories
- 277 procurement contracts with PhilGEPS tender data
- 45 DPWH projects with maps and status tracking
- 11 years of COA audit reports (2014–2024)
- Dual-language: English (root) and Filipino (`/fil/`)
- **202 pages** total (101 EN + 101 FIL)

**Live at:** [bettermapandan.org](https://bettermapandan.org) — deployed via GitHub Pages with a Hostinger-registered domain.

## Prerequisites

- **Python 3.11+** — required to run the build system and tests
- **Node.js 22+** — required only for image optimization (`optimize-images.mjs`) and Lighthouse audits

Python packages:

```bash
pip install -r requirements.txt
```

Node packages (for image optimization and Lighthouse):

```bash
npm install
```

This installs `lighthouse`, `chrome-launcher`, `puppeteer-core`, and `@lhci/cli`.

## Setup Steps

```bash
# 1. Clone the repository
git clone https://github.com/jadolation/bettermapandan.git
cd bettermapandan

# 2. Install Python dependencies
pip install -r requirements.txt

# 3. (Optional) Install Node dependencies for image optimization
npm install

# 4. Build the site
python3 build.py
```

Build output is written to the project root (EN pages) and `fil/` (FIL pages).

## How to Make Changes

### Pages

Edit HTML files in `src/pages/` or the generator files in `_build/generators/`. Use front matter for page metadata:

```html
---
title: Browser tab title
description: Meta description
---
<body content here>
```

### Locales (i18n)

- Edit `locales/en.json` and `locales/fil/fil.json`
- Run `python3 check_i18n.py` to verify key parity between the two files
- Run `python3 build.py --verify-translations` to check rendered output for missing translations

### CSS

- Edit partials in `assets/css/` (e.g., `tokens.css`, `nav.css`, `hero.css`, `cards.css`, `services.css`, `legislative.css`, `procurement.css`, `search.css`, `responsive.css`)
- Change design tokens in `tokens.css` (e.g., `--green-deep`, `--gold`, `--red-flag`) to re-theme the entire site

### JavaScript

- `assets/js/script.js` — main entry point (mobile nav, language switcher, weather widget, history carousel, barangay modals, accordions, feedback widget, Lucide icons)
- Feature-specific logic: `search.js`, `services.js`, `transparency.js`, `transparency-charts.js`, `procurement-table.js`, `leaflet-map.js`, `report.js`, `stats.js`, `legislative.js`, `common.js`

### Data

- Edit JSON files in `src/data/` (`services.json`, `legislative.json`, `procurement.json`, `dpwh.json`, `audit-reports.json`, `barangays.json`, `transparency-csv.json`)
- Data extraction scripts: `src/data/extract_procurement.py`, `src/data/extract_dpwh.py`, `src/data/generate_dpwh_seed.py`
- JSON Schema validators are defined in `src/data/schemas.py` — validation runs automatically during `python3 build.py` if `jsonschema` is installed

### Partial Templates

- `src/partials/base.html` — `<head>` + `<body>` shell with `{{TITLE}}`, `{{DESCRIPTION}}`, `{{HEADER}}`, `{{BODY}}`, `{{FOOTER}}`, `{{LANG_ATTR}}`, `{{CANONICAL_URL}}`, `{{ASSET_BASE}}`
- `src/partials/header.html` — Emergency bar + site nav (single source of truth)
- `src/partials/footer.html` — Site footer, includes `{{REPO_URL}}`

## Running Tests

```bash
# Run the full test suite with pytest
python3 -m pytest tests/ -v

# Run a specific test file
python3 -m pytest tests/test_locales.py -v
```

Test files:

- `tests/test_locales.py` — locale loading and translation
- `tests/test_generators.py` — page generators
- `tests/test_orchestrator.py` — breadcrumbs, heroes, page assembly
- `tests/test_templates.py` — template engine

## Running Quality Checks

```bash
# Lint Python code with ruff
ruff check .

# Cyclomatic complexity (target: 0 functions above threshold)
radon cc . -nd

# Maintainability index (target: Grade A/B across all modules)
radon mi .
```

These commands are also run in CI on every push and pull request via `.github/workflows/quality.yml`.

## Running Lighthouse Audits Locally

### Option A: Full local CI run (recommended)

```bash
# Build first
python3 build.py

# Start a local server (Python 3)
python3 -m http.server 9001

# In another terminal, run Lighthouse CI
npm run lighthouse
```

`lhci autorun` reads URLs and thresholds from `.lighthouserc.json` and asserts against:
- 11 URLs (homepage, services, government, legislative, statistics, transparency, search, report, about, and one Filipino service page)
- Performance >= 0.50 (warn)
- Accessibility >= 0.95 (error)
- Best Practices >= 0.90 (warn)
- SEO = 1.0 (error)
- FCP <= 2,000ms (warn)
- LCP <= 2,500ms (warn)
- CLS <= 0.1 (warn)
- TBT <= 300ms (warn)

### Option B: Single run (no caching)

```bash
npm run lighthouse:single
```

### Option C: Node image optimization only

```bash
node optimize-images.mjs
```

This compresses citizens-charter photos (mozjpeg, quality 70), history photos (PNG quality 60), and converts hero images and history PNGs to WebP.

## Contribution Workflow

1. **Fork** the repository on GitHub
2. **Clone** your fork locally
3. **Create a feature branch** from `main`:

   ```bash
   git checkout -b feature/your-feature-name
   ```

   Branch naming conventions:
   - `feature/` — new features
   - `fix/` — bug fixes
   - `docs/` — documentation changes
   - `refactor/` — code refactoring
   - `chore/` — tooling, dependencies, maintenance

4. **Make your changes** in `src/`, `locales/`, `assets/`, or `_build/`
5. **Build the site** to regenerate output:

   ```bash
   python3 build.py
   ```

6. **Run tests** to ensure nothing is broken:

   ```bash
   python3 -m pytest tests/ -v
   ruff check .
   ```

7. **Stage and commit** your changes (both source and regenerated output):

   ```bash
   git add .
   git commit -m "type(scope): description"
   ```

8. **Push** to your fork:

   ```bash
   git push origin feature/your-feature-name
   ```

9. **Open a Pull Request** to the `main` branch of `jadolation/bettermapandan`

10. CI will automatically run quality checks, build, and Lighthouse audits on your PR

## Code Style Guidelines

### Python

- Target Python 3.11+ (per project requirements)
- Line length: 100 characters (configured in `ruff.toml`)
- Use `ruff` for linting (see `ruff.toml` for configured rules)
- Prefer `pathlib.Path` over `os.path`
- Type hints are encouraged (seen in existing codebase)
- Avoid bare `except:` — the build system allows `BLE001` in `build.py` only via `[lint.per-file-ignores]`

### HTML

- Use 4-space indentation
- Front matter uses YAML delimiters (`---`)
- Keep partials small and focused (see `src/partials/`)
- Use semantic HTML where possible

### CSS

- 4-space indentation
- Modular partials in `assets/css/`
- Use design tokens from `tokens.css` instead of hardcoding colors

### JavaScript

- CommonJS modules (see `"type": "commonjs"` in `package.json`)
- Keep feature logic in dedicated files rather than adding to `script.js` if possible

### Locales

- Keep `locales/en.json` and `locales/fil.json` in sync — same keys, same nesting structure
- Use descriptive key names (e.g., `nav.services` rather than `s1`)

## Commit Message Conventions

Follow the [Conventional Commits](https://www.conventionalcommits.org/) format:

```
type(scope): description
```

**Types:**

| Type | When to use |
|------|-------------|
| `feat` | New feature |
| `fix` | Bug fix |
| `docs` | Documentation changes |
| `style` | Code style changes (formatting, missing semicolons) |
| `refactor` | Code refactoring |
| `chore` | Maintenance tasks, dependencies |
| `perf` | Performance improvements |
| `test` | Adding or updating tests |

**Examples:**

```
feat(services): add pharmacy category to services directory
fix(locales): sync missing fil.json keys for transparency page
docs(readme): update build commands
refactor(build): simplify search index generation
chore(ci): upgrade Lighthouse to v13
```

**Rules:**

- Use lowercase for the description
- Do not end the description with a period
- Scope is optional but recommended when relevant
- Keep the description concise (< 72 characters preferred)

## Reporting Issues

Found a bug, have a suggestion, or want to request a feature?

1. Check existing issues at [github.com/jadolation/bettermapandan/issues](https://github.com/jadolation/bettermapandan/issues) to avoid duplicates
2. Open a new issue with a clear title and description
3. For bug reports, include:
   - Steps to reproduce
   - Expected behavior
   - Actual behavior
   - Browser / device information if relevant
4. For feature requests, explain the use case and how it benefits the Mapandan community
